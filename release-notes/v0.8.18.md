# v0.8.18

本版把插件安装撞上 pnpm store 漂移的修复自动化了：本机 pnpm 大版本升级（如 10 → 11）会更换默认 store 目录（`store/v10` → `v11`），而 profile 的 node_modules 仍链在旧 store 上，pnpm 拒绝一切安装与卸载并报 `ERR_PNPM_UNEXPECTED_STORE`。此前 launcher 只给手动指引（自己去 profile 目录跑一次 `pnpm install`）；现在安装时检测到该失败会自动在 profile 目录以 `CI=true pnpm install` 重建依赖层，然后原样重试一次安装，全程在安装卡片的日志区可见，无需用户介入。

## Changes

- **store 漂移自动修复闭环**：安装失败按 pnpm 失败指纹识别 store 漂移（含同族的 `ERR_PNPM_PUBLIC_HOIST_PATTERN_DIFF`，同为 pnpm 大版本升级的 node_modules 形态漂移）后，先于构建脚本审批判定转内部修复信号：重建（`CI=true pnpm --dir <profile> install`，超时与安装同量级 15 分钟）→ 重试一次 `dsh plugin add` → 过同一安装护栏。重建命令与输出逐行进安装卡片日志区；审计台账新增 `repair-store` 行（命中原因与成败各留原始事实）
- **失败如实上报不循环**：重建失败（网络、权限等）按原因报错并保留原始输出；重建成功后重试仍报漂移则落回既有的手动修复提示文案，不做第二次循环
- **既有分流不变**：构建脚本拦截（审批对话框）、普通失败、取消、超时的路径与文案不受影响；漂移命中时若同时存在被拦构建脚本，修复后的重试会照常弹出审批对话框，两条闭环自然串接

## 验证

- `cargo test`：214 项全部通过（含 store 漂移分流新用例：真实报错原文与 hoist 形态均判入修复信号，构建脚本审批与普通失败两条既有分流不回归）
- `cargo clippy --all-targets`、`tsc`、`check:i18n`（593 key）、前端 `vitest`（230 项）通过
- ts-rs bindings 已同步（`InstallOutcome` 新增 `needsStoreRepair` 变体，内部信号，IPC 不可达）

## 升级说明

- **无破坏性变更、无迁移**。已装 profile 无需任何处理：下次安装/更新触发漂移报错时自动重建并继续
- 自动修复覆盖市场安装链（安装、更新、批量更新、审批后重装）。setup 阶段的授权插件安装仍走原有的清理重试闭环
- 若你在 dsh 运行期间手动升级过 pnpm 大版本，第一次安装可能比平时慢（重建整棵依赖树），属预期行为
